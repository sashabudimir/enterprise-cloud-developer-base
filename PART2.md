## Database design

- `coupons`: string partition key `coupon_id`, no table sort key.
- Provisioned capacity: 25 RCU and 10 WCU. A 1 KB item needs 0.5 RCU per
  eventually consistent read; 50 reads/second therefore require 25 RCU.
  Writes consume 1 WCU per 1 KB item; 10 writes/second need 10 WCU. The
  requirement's phrase "eventually consistent writes" is interpreted as normal
  writes; consistency modes apply to reads.
- `provider_campaign_index`: global secondary index with `provider_id` as its
  string partition key and `campaign_id` as its string sort key. ALL projection,
  25 RCU and 10 WCU. It supports an efficient Query by provider with an optional
  campaign condition. A query by campaign alone would require another index.
- The three supplied sample coupons are inserted only when missing. Rerunning
  the scripts preserves existing items.

## API behavior

`GET /coupons/{id}` calls DynamoDB GetItem and returns the matching coupon in
JSON, with HTTP 200. The sample shape is
`samples/t2_coupons_get_by_id_response.json`.

`PUT /coupons/{id}` accepts a JSON object containing one or more of `title`,
`description`, `coupon_code`, `campaign_id`, `provider_id`, `provider_name`,
`start_date`, `end_date`. Values are nonempty strings, matching the sample.
The existing record is updated with UpdateItem, preserving omitted fields;
HTTP 200 returns the updated coupon. A full sample coupon is also accepted
when its `coupon_id` matches the path. Changing its key is rejected.

Both endpoints return 400 for invalid input, 404 for an unknown coupon, and 500
for unexpected database failures. An UpdateItem condition prevents accidental
creation of unknown coupons. GET uses eventually consistent reads. Both public
methods use Lambda AWS_PROXY integrations (POST internally), with invocation
permissions and deployment to stage `local`.

The scripts reuse `coupons_lambda_role`, previously created in Part 1, and its
policy grants access to the coupons table and its indexes. CloudWatch logging
remains restricted to `/aws/lambda/coupons*`. Runtime dependencies are packaged
explicitly using AWS SDK for JavaScript v3. Development dependencies are omitted
from the Lambda ZIPs. The Lambda DynamoDB endpoint resolves inside LocalStack's
container network, rather than pointing at the Lambda container's loopback.

## Tests and evidence

There are 24 unit tests (7 retrieval, 17 update). SDK calls are mocked so tests
cover parameters, success, invalid input, not found and unavailable DynamoDB,
without depending on a database or credentials.

`newman_tests/coupons_part2_newman.json` exercises seven real HTTP requests:
GET, PUT, GET the persisted update, malformed JSON, missing coupon, update of a
missing coupon, and restoration of the original coupon. The same tests are
included as a Part 2 folder in `coupons_newman.json`. Use the standalone Part 2
collection when deploying only Part 2 into a fresh LocalStack instance.

The runner saves actual results under `evidence/part2/`:

- Both Jest JSON reports and the Newman JSON report.
- Table capacity, key schema, active GSI and a real index query.
- Lambda configuration and IAM policy.
- GET before an update, PUT response, GET after the persisted update, endpoint URL.

The evidence script restores the original coupon after its update demo.
These files are generated by your LocalStack run, not prefilled sample results.
If any command fails, keep its output and do not claim that deployment passed.
A passing unit test or local emulator test is not a LocalStack deployment result.
